# 006 — package-lock.json의 역할

> 정규 단계 05(설명). 이 자료는 설명만 담는다. `package.json`·`package-lock.json`은 아직 없고 설치·명령 실행도 하지 않았다. 아래 명령과 JSON은 모두 **아직 실행하지 않은 예시**다.

## 1. 현재 상태와 해결할 문제

### 지금 프로젝트

- 루트에 제목 한 줄을 표시하는 `index.html`만 있다. 외부 패키지는 쓰지 않으므로 기록할 설치 버전도 없다.
- [005 — package.json의 역할](005-package-json-role.md)에서 의존성과 실행 명령을 `package.json`에 기록한다고 정리했다. 실제 생성은 정규 단계 08에서 한다.

### 앞으로 생기는 문제

`package.json`의 의존성은 보통 정확한 버전 하나가 아니라 **허용 범위**로 적힌다. 예를 들어 `"vite": "^7.1.0"`처럼 `^`가 붙으면 호환 범위 안의 새 버전도 허용한다(예시 값이며 실제 버전은 08 단계에서 확인한다).

범위만 있으면 다음 문제가 생긴다.

1. **설치 시점마다 결과가 달라질 수 있다.** 오늘 설치한 사람과 한 달 뒤 설치한 사람(또는 Vercel 빌드 서버)이 같은 `package.json`으로 서로 다른 버전을 받을 수 있다.
2. **간접 의존성은 `package.json`에 없다.** Vite·React가 내부에서 쓰는 패키지(의존성의 의존성)는 우리 파일에 적히지 않는다. 이 패키지들의 버전도 설치 시점에 따라 바뀔 수 있다.
3. **"내 컴퓨터에서는 됐는데"를 추적하기 어렵다.** 무엇이 바뀌었는지 Git 기록으로 비교할 근거가 없다.

필요한 것은 "실제로 어떤 버전이 설치되었는가"를 트리 전체에 대해 기록하고 공유하는 파일이다.

## 2. 핵심 개념 — package-lock.json

`package-lock.json`(잠금 파일, lockfile)은 npm이 실제로 결정한 **의존성 트리 전체의 정확한 버전과 출처**를 기록하는 파일이다. 공식 문서는 목적을 이후 설치가 같은 트리를 만들 수 있도록 정확한 트리를 기술하는 것으로 설명한다.

### package.json과의 차이

| 구분 | package.json | package-lock.json |
| --- | --- | --- |
| 무엇을 적나 | 직접 쓰는 패키지와 **허용 버전 범위**, 실행 명령(scripts) 등 | 간접 의존성까지 포함한 **실제 설치 버전**, 다운로드 위치, 무결성 값 |
| 누가 작성하나 | 사람이 직접 작성하거나 npm 명령이 추가 | npm이 자동 생성·갱신. 손으로 편집하는 파일이 아니다 |
| 기준 역할 | 허용 범위의 **기준(source of truth)** | 그 범위 안에서 고른 결과를 **고정** |
| 배포(publish) | 패키지로 배포 가능 | 배포되지 않고 루트 프로젝트에서만 사용 |

npm install 문서의 요약이 핵심이다: `package-lock.json`은 의존성을 특정 버전으로 고정하지만, 허용 가능한 버전 범위의 기준은 `package.json`이다. 두 파일은 대체 관계가 아니라 함께 쓰는 관계다.

### 주요 필드(미실행 예시)

아래는 필드 구성을 보여 주기 위한 가상의 모양이다. 실제 내용은 08 단계에서 npm이 만든 파일로 확인한다.

```json
{
  "name": "learning-log",
  "version": "0.0.0",
  "lockfileVersion": 3,
  "requires": true,
  "packages": {
    "": {
      "name": "learning-log",
      "version": "0.0.0",
      "devDependencies": { "vite": "^7.1.0" }
    },
    "node_modules/vite": {
      "version": "7.1.x",
      "resolved": "https://registry.npmjs.org/vite/-/vite-7.1.x.tgz",
      "integrity": "sha512-...",
      "dev": true
    }
  }
}
```

- `lockfileVersion`: 잠금 파일 형식 버전. npm v9 이상은 `3`을 쓴다(v7~v8은 `2`, v5~v6은 `1`). 현재 확인된 npm `11.16.0`에서는 `3`이 예상되지만 실제 값은 생성 후 확인한다.
- `packages`: 설치될 패키지 위치를 키로 한 목록. 빈 문자열 `""` 키는 루트 프로젝트 자신이다.
- `version`: 실제 고른 정확한 버전(범위가 아님).
- `resolved`: 패키지를 받은 위치.
- `integrity`: 받은 파일이 기록된 것과 같은지 확인하는 해시 값.
- `dev`·`optional`: 개발 의존성·선택 의존성에만 속하는지 표시.

## 3. 생성·갱신 시점과 Git 공유

### 언제 생기고 바뀌나

- 공식 문서 기준: npm이 **`node_modules` 트리나 `package.json`을 수정하는 작업**을 하면 자동으로 생성된다. 예를 들어 `npm install vite`처럼 패키지를 추가하면 `package.json`과 함께 생성·갱신된다.
- 인자 없는 `npm install`은 잠금 파일에 기록된 버전이 `package.json` 범위를 만족하면 **잠금 파일의 정확한 버전을 사용**한다. 범위와 맞지 않으면(예: `package.json`의 범위를 직접 바꾼 경우) 범위에 맞는 새 버전을 골라 **잠금 파일을 갱신**한다.
- 따라서 `package-lock.json`의 변경은 "설치 결과가 바뀌었다"는 신호다. 의도한 변경인지 diff로 확인할 수 있다.

### 왜 Git에 넣나

공식 문서는 이 파일을 **소스 저장소에 커밋하도록 의도**했다고 명시하고, 그 이유로 다음을 든다.

- 팀원·배포 환경·CI가 같은 의존성 트리를 설치하도록 보장
- 설치된 패키지 폴더 자체를 커밋하지 않고도 과거 트리 상태로 돌아갈 수 있는 기록
- 트리 변화를 읽을 수 있는 diff로 확인
- 이미 기록된 메타데이터를 재사용해 설치 과정 최적화

이 프로젝트에서는 로컬 개발과 향후 Vercel 빌드(정규 단계 55~59)가 같은 버전을 쓰도록 하는 근거가 된다. 설치된 패키지 폴더를 버전 관리에서 제외하는 이유는 다음 단계 06에서 다룬다.

### npm ci와의 관계

`npm ci`는 잠금 파일을 전제로 하는 설치 명령이다. 공식 문서 기준:

- `package-lock.json` 또는 `npm-shrinkwrap.json`이 **반드시 있어야** 한다.
- `package.json`과 잠금 파일이 맞지 않으면 잠금 파일을 고치지 않고 **오류로 종료**한다.
- `package.json`과 잠금 파일에 **절대 쓰지 않는다**.
- 개별 패키지를 추가할 수 없고 프로젝트 전체만 설치한다.

즉 개발 중 패키지를 추가·변경할 때는 `npm install`로 잠금 파일을 갱신하고, 기록된 그대로 설치만 할 때는 `npm ci`를 쓸 수 있다. 이 프로젝트에서 어떤 명령을 어디에 쓸지는 08 단계와 배포 단계에서 실제 환경을 보고 정한다.

## 4. 대안 비교

| 방식 | 가능 여부 | 필요한 설정·제약 | 이번 선택 |
| --- | --- | --- | --- |
| 잠금 파일 없이 `package.json` 범위만 사용 | **가능**. `--no-package-lock`(설정 `package-lock=false`)이면 설치 시 잠금 파일을 무시하고 쓰지도 않는다 | 설치 시점마다 범위 안의 다른 버전, 특히 간접 의존성이 달라질 수 있다. `npm ci`는 잠금 파일이 필수라 **사용 불가** | 배포 환경과 버전을 맞출 근거가 없어 선택하지 않음 |
| `package.json`에 정확한 버전만 적기(`^` 없이) | **가능** | 직접 의존성만 고정되고 간접 의존성은 여전히 범위로 풀린다. 업데이트도 수동 | 트리 전체를 고정하지 못해 단독 사용하지 않음 |
| `npm-shrinkwrap.json` | **가능**. 형식은 잠금 파일과 같고 둘 다 있으면 이쪽이 우선 | 패키지와 함께 **배포**되는 용도. 이 프로젝트는 배포할 라이브러리가 아닌 웹 서비스 | 필요 없는 용도라 선택하지 않음 |
| 다른 패키지 관리자의 잠금 파일(`yarn.lock` 등) | 다른 도구를 쓰면 가능 | 도구가 바뀌어 [004](004-npm-role.md)의 npm 선택과 맞지 않음 | npm을 이미 선택했으므로 선택하지 않음 |
| **npm 기본 `package-lock.json`을 커밋** | **가능**, npm 기본 동작 | 추가 설정 없음. 파일을 손으로 고치지 않고 npm 명령으로만 바꾼다 | **선택** |

잠금 파일은 "npm을 쓰려면 반드시 있어야 하는 것"은 아니다. 없어도 설치는 된다. 다만 같은 설치 결과를 공유하려는 이 프로젝트의 목적에 가장 추가 비용이 적은 방식이라 기본 동작을 유지한다.

## 5. 재현성의 조건과 한계

잠금 파일은 설치될 **패키지 트리**를 고정하는 도구이며, 모든 실행 결과를 동일하게 만들지는 않는다.

- **잠금 파일과 package.json이 일치해야** 기록대로 설치된다. 불일치하면 `npm install`은 잠금 파일을 갱신하고, `npm ci`는 오류로 멈춘다.
- **설치 옵션도 같아야 한다.** 공식 `npm ci` 문서는 잠금 파일을 `--legacy-peer-deps`, `--install-links` 같은 옵션으로 만들었다면 `npm ci`에도 같은 옵션을 줘야 하며, 그렇지 않으면 오류가 날 가능성이 높다고 경고한다.
- **Node.js·npm 자체는 설치하지 않는다.** 잠금 파일이 기록하는 것은 프로젝트 패키지다. 실행하는 Node.js·npm 버전은 별도로 맞춰야 한다([003](003-nodejs-role.md), 현재 확인 버전은 [진행 상태](../progress.md) 참고).
- **커밋해야 공유된다.** 파일이 생성되어도 Git에 넣지 않으면 다른 환경은 그 기록을 받지 못한다.
- 운영체제별로 다른 선택 의존성이나 설치 스크립트 동작처럼 환경에 따른 차이는 이번 설명 단계에서 확인하지 않았다. 필요한 경우 08 단계의 실제 설치 결과로 확인한다.

## 6. 전체 흐름에서의 위치와 실제 작업 순서

| 단계 | 내용 | 파일 변화 |
| --- | --- | --- |
| 04 (완료) | package.json 설명 | 없음 |
| **05 (현재)** | package-lock.json 설명 | 학습자료만 추가 |
| 06 | node_modules 설명 | 학습자료만 추가 |
| 07 | Vite 설명 | 학습자료만 추가 |
| 08 | 최소 패키지 환경과 Vite 구성 | `package.json`, `package-lock.json`, `node_modules/` 생성 예정 |

08 단계에서 예상되는 순서(**미실행 예시**):

1. `package.json`을 만든다(방법은 [005](005-package-json-role.md)의 비교를 따라 08에서 결정).
2. `npm install -D vite`처럼 패키지를 추가한다 → npm이 `package.json`에 범위를 적고 `package-lock.json`을 생성한다.
3. 생성된 `package-lock.json`의 `lockfileVersion`과 `packages` 항목을 확인한다. 손으로 고치지 않는다.
4. 검토 후 `package.json`과 `package-lock.json`을 함께 커밋한다.
