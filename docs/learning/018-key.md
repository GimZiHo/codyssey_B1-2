# 018. key — 목록 항목에 안정적인 식별값을 붙인다

> 이 문서는 17단계 구현 전에 작성한 설명에 구현·검토 뒤 실제 변경과 브라우저 검증 결과를 보완한 것이다. "적용"·"확인 결과"는 실제 수행 결과이고, "key가 없거나 index일 때" 표는 공식 문서 기반 설명으로 이번에 직접 비교하지 않았다.

## 학습 목적

- 16단계 [배열 렌더링](017-array-rendering.md)에서 남긴 key 미지정 경고가 무엇을 요구하는지 이해한다.
- key가 "화면 순서"가 아니라 "데이터 항목"을 가리키게 해야 하는 이유를 안다.
- 현재 정적 배열에 어떤 값을 key로 줄지 정하고, 순서가 바뀌어도 같은 기록이 같은 DOM 요소로 이어지는지 확인하는 방법을 안다.

## 현재 문제

`src/pages/HomePage.jsx`는 records 배열 3개를 `map`으로 `li`에 옮긴다.

```jsx
{records.map((record) => <li>{record.title} ({record.project})</li>)}
```

각 `li`에 key가 없어서 개발 모드에서 React가 "목록의 각 자식에는 고유한 key가 필요하다"는 경고를 콘솔에 출력한다(16단계 검증에서 로드마다 1건 확인). 지금은 배열이 바뀌지 않으므로 화면은 정상이지만, 앞으로 원격 조회·등록·삭제로 목록이 바뀌면 문제가 드러난다.

## 핵심 개념

**key**: 배열로 만든 JSX 형제 요소 각각에 붙이는 문자열 또는 숫자 식별값이다. React는 다시 렌더링할 때 이전 목록과 새 목록의 요소를 key로 짝지어, 같은 key는 같은 항목으로 보고 기존 컴포넌트·DOM을 이어서 쓴다. 새 key는 새로 만들고 사라진 key는 제거한다.

React 공식 문서는 이를 바탕화면 파일 이름에 비유한다. 파일에 이름이 없고 "첫째, 둘째…"처럼 위치로만 부른다면 하나를 지우는 순간 나머지 번호가 모두 바뀐다. key는 파일 이름처럼 **위치가 바뀌어도 그 항목을 계속 가리키는 이름**이다.

### key가 없거나 index일 때

key를 주지 않으면 React는 배열 index(0, 1, 2 …)를 key처럼 사용한다. index는 "위치"이므로 항목이 추가·삭제·재정렬되면 같은 index가 다른 기록을 가리키게 된다.

| 상황 | key = 기록 id | key = index(미지정 포함) |
| --- | --- | --- |
| 순서만 바뀜 | 기존 `li`가 새 위치로 이동한다 | 위치별 `li`는 그대로 두고 안의 글자만 바꾼다 |
| 앞에 기록 추가 | 새 `li` 하나만 만든다 | 모든 위치의 내용이 한 칸씩 바뀐다 |
| 항목 안에 입력·상태가 있을 때 | 입력·상태가 해당 기록을 따라간다 | 입력·상태가 위치에 남아 다른 기록에 붙는다 |

현재 `li`에는 글자만 있어 눈에 보이는 차이는 없다. 하지만 이후 단계에서 항목에 입력이나 상태가 생기면 index key는 "다른 기록에 입력값이 붙는" 오류로 이어진다. 공식 문서도 index key가 미묘하고 혼란스러운 버그로 이어지기 쉽다고 설명한다.

### key 규칙

공식 문서의 두 가지 규칙이다.

1. **형제 사이에서 고유해야 한다.** 같은 배열 안에서만 겹치지 않으면 되고, 다른 배열의 key와는 겹쳐도 된다.
2. **바뀌지 않아야 한다.** 렌더링할 때마다 새로 만들면 안 된다. `key={Math.random()}`처럼 매번 다른 값을 주면 이전·다음 렌더링의 key가 절대 일치하지 않아 모든 항목의 DOM을 매번 새로 만들고, 항목 안의 사용자 입력도 잃는다.

또한 key는 React가 내부에서만 쓰는 표시다. 컴포넌트는 `key`를 props로 받지 못하므로, 항목 컴포넌트가 id를 써야 한다면 `key={id} recordId={id}`처럼 별도 prop으로 따로 넘겨야 한다. 이번 단계는 항목 컴포넌트를 만들지 않으므로 해당하지 않는다.

### key 값은 어디서 오는가

| 데이터 출처 | 공식 문서가 권하는 key | 현재 프로젝트 |
| --- | --- | --- |
| 데이터베이스 | 데이터베이스의 키·ID(본래 고유) | 원격 조회 단계(35단계 이후)에서 Supabase 행의 식별자로 바꾼다 |
| 로컬에서 만들어 저장하는 데이터 | 증가 카운터, `crypto.randomUUID()`, `uuid` 패키지 — **항목을 만들 때** 한 번 생성 | 해당 없음 |
| 코드에 고정한 정적 데이터 | 데이터 자체에 id를 적어 둔다 | 이번 단계의 선택 |

## 대안 비교

| 방식 | 가능 여부 | 이번에 선택하지 않은 이유 |
| --- | --- | --- |
| key 미지정 유지 | 가능(경고만 출력, 화면은 표시) | 경고가 남고 index 방식과 같은 문제가 있다 |
| `key={index}` | 가능(경고가 사라짐) | 경고만 숨길 뿐 위치를 식별값으로 쓰는 문제는 그대로다 |
| `key={record.title}` | 현재 3개는 제목이 달라 가능 | 제목은 수정 기능(49단계)에서 바뀔 수 있고 같은 제목의 기록도 허용될 수 있어 "고유·불변" 조건을 보장하지 못한다 |
| `key={Math.random()}`, 렌더링 중 `crypto.randomUUID()` | 문법상 가능 | 렌더링마다 key가 바뀌어 규칙 2를 어긴다 |
| records에 `id` 필드를 추가하고 `key={record.id}` | 가능 | **선택**. 데이터가 스스로 식별값을 가지며, 나중에 원격 데이터의 id로 같은 자리를 대체할 수 있다 |

id의 최종 형식(숫자·UUID 등)은 28단계 데이터 모델에서 확정한다. 이번에는 정적 예시 데이터 안에서만 고유하면 되므로 기록을 구분하는 짧은 문자열을 쓴다.

## 적용

실제 변경 파일은 `src/pages/HomePage.jsx` 하나다. `main.jsx`·`PageTitle.jsx`·`index.html`·패키지·Vite 설정은 바꾸지 않았고, 이벤트·state·새 패키지도 추가하지 않았다(18·19단계).

```jsx
// src/pages/HomePage.jsx (실제 변경 후 핵심 부분)
// id: 기록마다 고정된 고유 식별값. 위치(index)가 아닌 데이터로 항목을 구분한다.
const records = [
  { id: 'jsx', title: 'JSX', project: 'B1-2' },
  { id: 'function-component', title: '함수 컴포넌트', project: 'B1-2' },
  { id: 'props', title: 'props', project: 'B1-2' },
];

// key: 다시 렌더링할 때 React가 같은 기록의 li를 짝지어 재사용하게 하는 표시.
{records.map((record) => (
  <li key={record.id}>{record.title} ({record.project})</li>
))}
```

- `id`: 세 기록이 `'jsx'`·`'function-component'`·`'props'`로 배열 안에서 겹치지 않고, 렌더링과 무관하게 코드에 고정된 값이다.
- `key={record.id}`: `map` 콜백이 반환하는 가장 바깥 요소(`li`)에 붙였다. key는 `map` 안의 요소에 두어야 하며, `li` 안쪽 요소나 `ul`에 두면 효과가 없다.
- 화면에 표시하는 내용(`title (project)`)과 `div > PageTitle + ul` 구조는 16단계와 같다. `id`는 화면에 보이지 않고 key로만 쓰인다.

## 실행 흐름

1. 첫 렌더링: React는 `li` 3개를 만들고 각 요소를 key(`record.id`)와 함께 기억한다.
2. 다시 렌더링: `map`이 새 `li` 요소 배열을 반환한다.
3. React는 새 배열의 key를 이전 key와 비교한다. 같은 key → 기존 DOM `li`를 재사용(필요하면 위치 이동·내용 갱신), 새 key → 생성, 없어진 key → 제거.
4. 따라서 순서만 바뀐 경우 새 DOM을 만들지 않고 기존 `li` 3개를 새 순서로 옮긴다.

현재 records는 바뀌지 않으므로 실제 서비스 화면에서 3~4번은 일어나지 않는다. 그래서 검증에서는 제품 코드에 state·이벤트를 넣지 않고, 같은 React 루트에 순서를 바꾼 목록을 다시 렌더링해 4번을 확인했다(아래 확인 결과).

## 질문·추가 확인

- index key와 id key의 차이는 항목에 입력이나 상태가 있을 때 눈에 보인다. 해당 기능이 생기는 단계(19단계 state, 43단계 controlled input)에서 다시 확인할 수 있다.
- 원격 데이터로 바꾼 뒤 key를 어떤 필드로 둘지는 28단계 데이터 모델에서 정한다.
