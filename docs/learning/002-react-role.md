# 002. React의 역할 — 정적 화면에서 데이터에 따라 바뀌는 화면으로

> 단계: [진행 상태](../progress.md)의 **01 — React의 역할(설명)**.
> 이번 단계는 설명만 한다. React·npm·Vite 설치와 소스 변경은 하지 않았으며, 아래의 코드와 화면 흐름은 **모두 아직 구현하지 않은 예시**다.

## 1. 현재 상태와 해결할 문제

### 지금 있는 것

현재 프로젝트의 화면은 [`index.html`](../../index.html) 하나이고, 본문에는 제목 한 줄만 있다([001 자료](001-index-html.md)).

```html
<body>
  <h1>학습 기록 서비스</h1>
</body>
```

이 화면은 **정적 화면**이다. 정적(static)이란 브라우저가 HTML 파일을 읽어 한 번 그린 뒤, 파일을 고치지 않는 한 표시 내용이 바뀌지 않는다는 뜻이다. 사용자가 무엇을 입력하거나 서버의 데이터가 바뀌어도 이 화면은 스스로 달라지지 않는다.

### 앞으로 필요한 것

이 과제의 서비스는 B1-1·B1-2 학습자료를 담는 **학습 기록 CRUD**(Create 등록 · Read 조회 · Update 수정 · Delete 삭제) 서비스다. 진행 상태에 정리된 요구를 화면 관점으로 바꾸면 다음과 같다.

| 상황 | 화면에서 일어나야 하는 변화 |
| --- | --- |
| 목록을 원격에서 불러올 때 | "불러오는 중" 표시 → 성공하면 기록 목록, 실패하면 오류 안내, 0건이면 빈 목록 안내 |
| 기록을 등록·수정할 때 | 입력할 때마다 입력값 반영, 필수값 누락 시 오류 표시, 전송 중 버튼 비활성화 |
| 기록을 삭제할 때 | 목록에서 해당 항목 제거, 실패하면 오류 표시 |
| 페이지를 이동할 때 | 주소에 따라 홈·목록·상세·등록·수정·Not Found 중 하나를 표시 |

즉 앞으로의 화면은 **데이터와 사용자 동작에 따라 계속 다시 그려져야 한다.** 과제가 강조하는 **이벤트 → 상태 변경 → 렌더링**도 이 흐름을 가리킨다. 여기서 렌더링(rendering)은 "현재 데이터에 맞게 화면을 그리는 일"로 이해하면 된다. 이 흐름을 코드로 어떻게 표현하는지는 이후 단계에서 하나씩 다루며, 이번 자료에서는 문법을 설명하지 않는다.

해결할 문제는 다음 한 문장으로 정리할 수 있다.

> 데이터가 바뀔 때마다 화면을 **누가, 어떤 방식으로** 맞춰 줄 것인가?

## 2. 기존 방식과 대안 비교

### 2-1. 정적 HTML만 유지 — 불가능

HTML은 화면의 구조를 적는 문서다. 파일에 적힌 내용만 표시하므로 원격 데이터를 불러와 목록을 만들거나, 입력에 따라 오류를 보여 주거나, 등록 결과를 반영할 수 없다. 원격 CRUD 요구를 만족할 수 없으므로 **기술적으로 불가능한 대안**이다. HTML은 앞으로도 브라우저가 처음 읽는 진입 파일로 남지만, 화면을 바꾸는 역할은 JavaScript가 맡아야 한다.

### 2-2. 순수 JavaScript로 DOM 직접 조작 — 가능하지만 선택하지 않음

순수 JavaScript(라이브러리 없이 브라우저 기본 기능만 쓰는 JavaScript)로도 이 서비스는 **구현할 수 있다.** 브라우저는 HTML을 읽어 DOM(Document Object Model, 화면 요소를 JavaScript에서 다룰 수 있게 만든 객체 구조)을 만들고, JavaScript는 DOM API로 요소를 찾고 만들고 지우고 속성을 바꿀 수 있기 때문이다. 추가 설치나 빌드 도구도 필요 없다. `<script>` 태그 하나로 시작할 수 있다.

대신 **화면을 데이터에 맞추는 모든 과정을 직접 명령해야 한다.** 예를 들어 목록 조회 하나만 해도 다음 순서를 직접 써야 한다. (미구현 예시)

```js
// 아직 구현하지 않은 예시: 순수 JavaScript로 목록 조회 화면을 직접 바꾸는 흐름
loading.hidden = false;          // 1. 로딩 표시를 켠다
errorBox.hidden = true;          // 2. 이전 오류 표시를 끈다
list.replaceChildren();          // 3. 이전 목록 항목을 지운다

const records = await fetchRecords();   // 원격 조회(가상의 함수)

loading.hidden = true;           // 4. 로딩 표시를 끈다
if (records.length === 0) {
  emptyBox.hidden = false;       // 5-a. 0건이면 빈 목록 안내를 켠다
} else {
  emptyBox.hidden = true;        // 5-b. 아니면 안내를 끄고
  for (const record of records) {
    const li = document.createElement('li');   // 항목 요소를 직접 만들어
    li.textContent = record.title;
    list.append(li);                            // 목록에 직접 붙인다
  }
}
// 실패 처리, 재시도, 삭제 후 항목 제거, 수정 후 항목 갱신도 각각 따로 작성해야 한다.
```

직접 DOM 관리에서 개발자가 책임져야 하는 부분은 다음과 같다.

| 직접 관리할 일 | 놓쳤을 때 생기는 문제 |
| --- | --- |
| 로딩·오류·빈 목록·결과 표시를 상황마다 켜고 끄기 | 로딩이 끝났는데 "불러오는 중"과 목록이 함께 보이는 등 서로 모순된 화면 |
| 데이터 배열과 화면 목록 항목을 일치시키기 | 삭제·수정 후 화면에 이전 항목이 남거나 중복됨 |
| 입력값·검증 오류·전송 중 버튼 상태를 동기화하기 | 오류가 해결됐는데 메시지가 남거나, 전송 중에 다시 제출됨 |
| 주소에 맞는 페이지 영역 교체하기 | 이전 페이지의 요소나 이벤트가 남음 |

React 공식 문서는 이런 방식을 **명령형(imperative) UI**라고 부르고, 옆 좌석에서 운전자에게 "여기서 좌회전, 다음에 우회전"처럼 길을 하나하나 지시하는 것에 비유한다. 또한 이 방식이 "고립된 예제에서는 충분히 잘 동작하지만, 더 복잡한 시스템에서는 관리가 기하급수적으로 어려워진다"고 설명한다([React — Reacting to Input with State](https://react.dev/learn/reacting-to-input-with-state#how-declarative-ui-compares-to-imperative)).

**선택하지 않은 이유**

1. 과제의 기술 요구가 **React 18 이상**이다. 순수 JavaScript는 기술적으로 가능하지만 이 요구를 만족하지 못한다. B1-1의 순수 JavaScript·라이브러리 금지 조건은 이번 과제에 계승하지 않는다.
2. 5개 페이지와 Not Found, 원격 CRUD, 로딩·오류·빈 상태 UI를 모두 직접 명령으로 맞추면, 위 표의 동기화 작업이 화면 수만큼 늘어난다.

### 2-3. 다른 UI 라이브러리 — 가능하지만 이번 과제에서는 해당 없음

다른 UI 라이브러리도 "데이터에 따라 화면을 갱신한다"는 같은 문제를 해결할 수 있다. 하지만 이번 과제는 React 18 이상을 명시하므로 비교 대상으로 깊게 다루지 않는다. 기술적으로 불가능해서가 아니라 **요구사항 때문에 선택지에서 제외**된다.

### 비교 요약

| 대안 | 가능 여부 | 필요한 추가 구성 | 제약 | 이번 판단 |
| --- | --- | --- | --- | --- |
| 정적 HTML만 유지 | 불가능 | 없음 | 데이터에 따라 화면을 바꿀 수 없음 | 제외 |
| 순수 JavaScript DOM 조작 | 가능 | 없음(`<script>`만으로 시작) | 모든 화면 변화를 직접 명령·동기화 | React 18 이상 요구 불충족, 관리 부담 → 미선택 |
| 다른 UI 라이브러리 | 가능 | 해당 도구의 설치·설정 | 과제 기술 요구와 다름 | 요구사항 때문에 제외 |
| React 18 이상 | 가능 | 패키지 설치·개발 도구·JSX 변환 설정(이후 단계) | 도입 준비 단계가 필요 | **선택** |

## 3. React 선택 근거 — React가 맡는 역할

React는 사용자 인터페이스(UI)를 만들기 위한 JavaScript 라이브러리다. 공식 문서의 표현으로는, React에서는 UI를 직접 조작하지 않는다. 즉 컴포넌트를 직접 켜거나 끄거나 보이거나 숨기지 않고, **무엇을 보여 주고 싶은지 선언하면 React가 UI를 어떻게 갱신할지 알아낸다.** 문서는 이를 택시 기사에게 목적지만 말하고 길은 맡기는 것에 비유한다([같은 문서](https://react.dev/learn/reacting-to-input-with-state#how-declarative-ui-compares-to-imperative)). 이런 방식을 **선언형(declarative) UI**라고 한다.

앞의 목록 조회를 선언형으로 생각하면, 개발자가 적는 내용은 "요소를 켜고 끄는 순서"가 아니라 **"각 상황에서 화면이 어떤 모습이어야 하는가"**다. (미구현 예시, 문법 없이 설명)

| 현재 데이터 상황 | 원하는 화면 |
| --- | --- |
| 불러오는 중 | 로딩 안내만 표시 |
| 실패 | 오류 안내와 재시도 버튼 |
| 성공, 0건 | 빈 목록 안내 |
| 성공, 1건 이상 | 기록 제목 목록 |

데이터가 한 상황에서 다른 상황으로 바뀌면, 이전 화면에서 무엇을 지우고 무엇을 새로 만들지는 React가 계산해 실제 DOM에 반영한다. 그래서 2-2 표의 "모순된 화면"이나 "남은 이전 항목" 같은 동기화 실수를 개발자가 매번 직접 막을 필요가 줄어든다.

정리하면 이번 React 선택 근거는 두 가지다.

1. **요구사항**: 과제가 React 18 이상을 요구한다. 이것이 선택의 직접적인 이유이며, 기술적으로 React만 가능해서가 아니다.
2. **문제와의 적합성**: 이 서비스의 핵심 문제는 "데이터가 바뀔 때 화면을 맞추는 일"이고, React는 원하는 화면을 선언하면 갱신을 대신 처리하는 역할을 맡는다. 과제가 강조하는 이벤트 → 상태 변경 → 렌더링 흐름도 이 역할 위에서 학습한다.

React를 쓴다고 해서 HTML이나 JavaScript가 사라지지는 않는다. 브라우저는 여전히 `index.html`을 먼저 읽고, 화면을 그리는 코드는 JavaScript로 작성한다. React는 그 JavaScript 안에서 "화면 갱신 방법"을 맡는 라이브러리다.

## 4. 실제 작업 순서

React는 아직 설치하지 않았고, `package.json`도 없다. 진행 상태의 작업 단계 기준으로 React 도입까지의 흐름은 다음과 같다. 각 단계의 개념은 해당 단계 자료에서 다룬다.

| 단계 | 구분 | 내용 | 생성·변경 파일 |
| --- | --- | --- | --- |
| **01 (현재)** | 설명 | React의 역할(이 자료) | 이 자료와 [자료 목록](README.md)만 추가·수정 |
| 02–07 | 설명 | 개발 도구 실행 환경과 패키지 관리, 개발·빌드 도구 | 없음(설명 단계) |
| 08 | 변경 | 최소 패키지 환경과 개발 서버 구성, 기존 HTML 표시 확인 | 해당 단계에서 확정 |
| 09–14 | 설명·변경 | 모듈, React 루트 연결, JSX, 함수 컴포넌트 | 해당 단계에서 확정 |
| 15 이후 | 변경 | props, 목록, 이벤트, state 등 화면 갱신 흐름 구현 | 해당 단계에서 확정 |

이번 단계에서 실제로 수행한 일은 이 학습자료 작성과 자료 목록 연결뿐이다. `index.html`은 바뀌지 않았고, 설치·실행·브라우저 검증은 하지 않았다(설명 단계라 해당 없음).
