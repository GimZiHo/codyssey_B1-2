# 007 — node_modules의 역할

- **현재 단계**: 정규 단계 06 — node_modules(설명 단계). 설치·설정 생성·소스 변경·실행 검증은 하지 않았다.
- **다음 단계**: 07 — Vite(설명), 실제 패키지 설치는 08 단계에서 한다.
- **이 문서의 예시**: 명령·디렉터리 구조는 모두 **아직 실행하지 않은 예시**다. 실제 결과가 아니다.

## 1. 학습 목적

npm으로 설치한 패키지 파일이 **어디에 놓이는지**, 그 폴더가 [package.json](005-package-json-role.md)·[package-lock.json](006-package-lock-json-role.md)과 **어떻게 역할이 다른지**, 그리고 이 프로젝트가 그 폴더를 **Git에 넣지 않고 필요할 때 다시 설치하는 방식**을 선택한 이유를 이해한다.

## 2. 현재 상태와 해결할 문제

### 현재 프로젝트 상태 (2026-09-27 확인)

- 저장소 루트에는 `index.html`과 `.gitignore`가 있다. `package.json`·`package-lock.json`·`node_modules`는 **없다**. npm 환경은 아직 도입하지 않았다.
- 기존 `.gitignore`에는 이미 `node_modules/` 줄이 들어 있다. 이 단계에서 만든 것이 아니라 이전에 있던 설정을 읽어 확인한 것이다.
- 지금 `index.html`은 B1-1처럼 **브라우저로 파일을 직접 열어** 표시할 수 있고, 실제로 그렇게 검증했다([001](001-index-html.md)). npm 설치 없이도 이 방식은 계속 동작한다.

### 앞으로 생길 문제

08 단계에서 Vite를 npm으로 설치하면 Vite 자신과 Vite가 의존하는 다른 패키지들의 **실제 코드 파일**이 프로젝트 안 어딘가에 놓여야 한다. `package.json`은 "무엇이 필요한가"를, `package-lock.json`은 "정확히 어떤 버전 트리였는가"를 적은 **기록**일 뿐이고, 실행할 코드 자체는 들어 있지 않다. 그래서 다음 질문에 답해야 한다.

1. 설치된 패키지 파일은 어디에 두는가?
2. 그 폴더를 Git 저장소에 함께 올릴 것인가?
3. 올리지 않는다면 다른 컴퓨터나 배포 환경에서는 어떻게 같은 파일을 다시 얻는가?

## 3. 핵심 개념 — node_modules

**node_modules**는 npm이 로컬 설치(프로젝트 안 설치)한 패키지의 실제 파일을 두는 폴더다.

- **위치**: npm 공식 문서는 로컬 설치(기본값)가 "현재 패키지 루트의 `./node_modules`"에 파일을 둔다고 설명한다. 패키지 루트란 `package.json`이 있는 폴더를 말한다. 이 프로젝트에서는 저장소 루트가 된다.
- **실행 파일**: 로컬 모드에서 패키지가 제공하는 명령 실행 파일은 `./node_modules/.bin`에 연결되어, npm으로 실행하는 scripts에서 사용할 수 있다. 08 단계에서 `package.json`의 scripts로 Vite를 실행할 때 이 경로가 쓰인다.
- **중첩과 끌어올림(hoisting)**: 패키지가 다른 패키지에 의존하면 그 의존성도 함께 설치된다. npm 3 이후로는 가능한 한 상위의 `node_modules`에 의존성을 끌어올려 같은 패키지의 중복 설치를 줄인다. 그래서 직접 설치한 패키지가 하나여도 `node_modules` 안에는 여러 폴더가 생길 수 있다.

아래는 08 단계 이후 생길 수 있는 구조의 **미실행 예시**다. 실제 폴더 이름과 개수는 설치 결과에 따라 다르다.

```text
codyssey_B1-2/            ← 패키지 루트 (package.json 위치)
├── index.html
├── package.json          ← 필요한 패키지와 버전 범위 기록
├── package-lock.json     ← 실제 설치된 의존성 트리 기록
└── node_modules/         ← 설치된 패키지의 실제 파일
    ├── .bin/             ← 패키지 명령 실행 파일 연결 (예: vite)
    ├── vite/
    └── (Vite가 의존하는 다른 패키지들)
```

### 세 가지의 역할 차이

| 대상 | 담는 것 | 누가 만드나 | Git 추적 (이 프로젝트 선택) |
| --- | --- | --- | --- |
| `package.json` | 필요한 패키지 이름·버전 범위, 실행 명령 | 사람이 작성하거나 npm 명령이 갱신 | 추적한다 |
| `package-lock.json` | 실제 설치된 의존성 트리의 정확한 버전·출처 | npm이 설치할 때 생성·갱신 | 추적한다 |
| `node_modules/` | 패키지의 실제 코드 파일 | npm이 위 두 기록을 바탕으로 설치 | 추적하지 않는다 |

앞의 두 파일은 **무엇을 설치할지의 기록**, `node_modules`는 **그 기록으로 설치한 결과물**이다. 기록만 있으면 결과물은 다시 만들 수 있다는 점이 아래 선택의 출발점이다.

## 4. 기존 방식과 대안 비교

### B1-1과 지금의 차이

B1-1은 라이브러리를 쓰지 않고 HTML·CSS·JavaScript 파일을 브라우저로 직접 열었다. 설치할 패키지가 없었으므로 `node_modules`도 필요 없었다. B1-2의 지금 `index.html`도 같은 방식으로 열 수 있다. npm으로 패키지를 설치하는 순간부터 `node_modules`가 생기며, 그 전까지는 이 문서의 선택이 실제로 적용될 대상이 없다.

### 설치 파일을 두는 위치

| 방식 | 가능 여부 | 필요한 조건·제약 | 이번 선택 |
| --- | --- | --- | --- |
| 로컬 설치 → 패키지 루트의 `node_modules` | 가능, npm 기본값 | 프로젝트마다 따로 설치되어 프로젝트 간 버전이 섞이지 않는다. 설치한 만큼 디스크를 쓴다. | **선택** |
| 전역 설치 (`npm install -g`) | 가능 | 컴퓨터 전체에서 한 버전을 공유한다. 프로젝트별 버전 기록·재현과 연결되지 않는다. | 선택하지 않음. 프로젝트 의존성은 프로젝트에 두는 방침이다. |
| 파일을 직접 내려받아 폴더에 복사 | 가능 | 의존성 트리와 버전을 사람이 관리해야 한다. [004](004-npm-role.md)에서 npm을 선택한 이유와 같다. | 선택하지 않음 |

이 문서는 npm 로컬 설치를 선택한 범위 안에서 `node_modules`를 설명한다. 다른 패키지 관리자의 설치 방식은 다루지 않는다.

### node_modules를 Git에 넣을 것인가

| 방식 | 가능 여부 | 장점 | 제약 | 이번 선택 |
| --- | --- | --- | --- | --- |
| Git에서 제외하고 필요할 때 재설치 | 가능 | 저장소에는 기록 파일만 남아 작고, 변경 이력이 소스 중심으로 유지된다. | 새 환경마다 설치 명령과 네트워크가 필요하다. | **선택** |
| `node_modules`를 Git에 커밋 | **가능하다** (Git이 막지 않는다) | 설치 없이 바로 파일이 있다. | 수많은 파일이 저장소와 커밋 diff에 들어간다. 운영체제별로 설치 결과가 달라질 수 있는 패키지는 다른 환경에서 맞지 않을 수 있다. 버전을 바꿀 때마다 대량 변경이 생긴다. | 선택하지 않음 |

`node_modules`를 Git에 넣는 것은 **불가능해서가 아니라 이번 프로젝트에서 선택하지 않은 방식**이다. 이 프로젝트는 `package.json`·`package-lock.json`으로 설치 결과를 다시 만들 수 있으므로 결과물까지 저장소에 넣을 필요가 없다고 판단했다.

## 5. 선택 근거

- **다시 만들 수 있는 것은 저장하지 않는다**: `package-lock.json`이 정확한 의존성 트리를 기록하므로 `node_modules`는 언제든 재설치로 복원할 수 있다([006](006-package-lock-json-role.md)).
- **재설치 명령이 공식적으로 제공된다**: npm 공식 문서에 따르면 `npm ci`는
  - `package-lock.json`(또는 `npm-shrinkwrap.json`)이 **반드시** 있어야 하고,
  - lock 내용이 `package.json`과 맞지 않으면 lock을 고치지 않고 **오류로 종료**하며,
  - 이미 `node_modules`가 있으면 설치 전에 **자동으로 제거**하고,
  - `package.json`이나 lock 파일을 **절대 수정하지 않는다**.
  즉 기록 파일만 공유하면 다른 환경에서도 기록대로 `node_modules`를 새로 만들 수 있다.
- **이미 준비된 설정과 일치한다**: 기존 `.gitignore`의 `node_modules/` 줄이 이 선택을 반영한다. 설치 후 Git 상태에 `node_modules`가 나타나지 않는지는 08 단계에서 실제로 확인한다.

## 6. 실제 작업 순서

| 단계 | 내용 | 생성·변경되는 파일 | 상태 |
| --- | --- | --- | --- |
| 06 (현재) | node_modules 개념 설명 | 이 학습자료와 자료 목록만 | 자료 작성 |
| 07 | Vite 설명 | 학습자료만 | 대기 |
| 08 | 최소 패키지 환경과 Vite 실행 명령 구성 | `package.json`, `package-lock.json`, `node_modules/` | 대기 |

08 단계 이후의 흐름을 **미실행 예시**로 정리하면 다음과 같다. 실제 명령과 인자는 08 단계에서 결정한다.

```bash
# (미실행 예시) 처음 패키지를 추가할 때: node_modules 생성, package.json·package-lock.json 기록·갱신
npm install <패키지>

# (미실행 예시) 저장소를 새로 받은 환경에서 lock 그대로 재설치: node_modules를 지우고 다시 만든다
npm ci
```

- 처음 설치할 때는 [004](004-npm-role.md)에서 다룬 `npm install`이 `node_modules`를 만들고 두 기록 파일을 작성·갱신한다.
- Git에는 `package.json`·`package-lock.json`만 커밋하고, `node_modules/`는 `.gitignore` 설정으로 추적하지 않는다.
- 다른 컴퓨터나 배포 환경에서는 저장소를 받은 뒤 `npm ci`(또는 `npm install`)로 `node_modules`를 다시 만든다.
- `node_modules`가 꼬였다고 의심될 때도 폴더를 지우고 기록 파일로 재설치하면 된다. 기록 파일이 원본이고 `node_modules`는 결과물이기 때문이다.

## 7. 확인 결과와 남은 확인

- **이번 단계 확인**: 저장소 루트 파일 목록과 기존 `.gitignore` 내용을 읽어 `node_modules`가 아직 없고 제외 설정이 이미 있음을 확인했다. 설명 단계이므로 설치·실행 검증은 해당하지 않는다.
- **08 단계에서 확인할 것**: 실제 `node_modules` 생성 위치, `.bin`에 연결된 Vite 실행 파일, `git status`에 `node_modules`가 나타나지 않는지.
- 이 자료를 작성했다고 해서 개념 이해가 완료되었다고 보지 않는다. 궁금한 점은 질문으로 이어 가면 이 자료에 보완한다.
