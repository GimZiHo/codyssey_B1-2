## 1. 과제의 성격

B1-2는 React 기반 SPA 서비스 1개를 만드는 선택 과제다. B1-1에서 익힌 이벤트 → 상태 변경 → 화면 업데이트 흐름을 이어서 학습하지만, B1-1 포트폴리오에 기능을 추가하라는 요구는 없다.

PDF 1쪽은 최종 결과물을 React 기반 웹 서비스로 정하고, 3쪽은 React 프로젝트로 시작하며 서비스 주제는 학습자가 직접 정하도록 명시한다. 따라서 별도의 후속 프로젝트로 해석한다. 명시된 학습시간은 80시간이며 실제 소요시간을 예측한 값은 아니다.

별도 저장소 제출 의무나 기존 결과물 재사용에 관한 별도 규정은 PDF에 명시되어 있지 않다. 프로젝트 분리는 요구사항 자체가 아니라 B1-1을 보존하고 기술 제약의 충돌을 피하기 위한 진행 결정이다.

## 3. 필수 요구사항

B1-2 수행 여부는 선택이지만, 수행한다면 기본 요구사항을 모두 충족해야 한다. 아래 목록은 분석 요약이며 구현 완료 체크리스트가 아니다.

### 프로젝트와 컴포넌트 — PDF 3쪽, 5~6쪽

- React 18 이상으로 구현한다.
- 서비스 주제는 직접 정하되 단일 핵심 데이터 CRUD가 가능한 수준으로 제한한다.
- pages, components, hooks 또는 lib의 역할을 분리한다.
- 주요 페이지에 공통 헤더·내비게이션 등의 레이아웃을 적용한다.
- 최소 8개의 재사용 컴포넌트를 구성한다.
- 재사용 컴포넌트는 최소 1개 이상의 prop을 받아 표시나 동작이 달라져야 한다.
- 페이지 컴포넌트와 UI 컴포넌트를 분리한다.
- 로딩·에러·빈 상태 UI는 재사용 컴포넌트로 통일한다.

### 라우팅 — PDF 2~3쪽

- 최소 5개 페이지 라우트가 동작해야 한다.
- 목록과 상세 라우트를 포함한다.
- 잘못된 주소에는 Not Found 페이지를 표시한다.
- 내비게이션으로 주요 라우트에 이동할 수 있어야 한다.
- 예시의 /login은 로그인 필수를 의미하지 않는다. 인증은 보너스다.

### 상태와 렌더링 — PDF 3~4쪽

- 폼 입력을 controlled input으로 관리한다.
- 목록·상세 데이터와 로딩·에러를 React 상태로 관리한다.
- 데이터 조회·갱신 흐름 중 최소 1개를 커스텀 훅으로 분리한다.
- 사용자 이벤트 → 상태 변경 → 렌더링 변화가 최소 3곳에서 명확히 드러나야 한다.
- 핵심 화면에서 로딩·에러·빈 상태를 일관되게 처리한다.

### 원격 CRUD와 폼 — PDF 4쪽

- Supabase 또는 Firebase 중 하나를 사용한다.
- 핵심 데이터의 등록·조회·수정·삭제가 반드시 원격 데이터 기준으로 동작해야 한다.
- 목록을 표시하고, 상세 화면은 라우트 파라미터로 특정 데이터를 조회한다.
- 등록·수정 성공 시 이동 또는 갱신하고, 삭제 후 목록 갱신 또는 이동한다.
- 등록·수정 폼에 필수값 검증과 오류 표시를 구현한다.
- 제출 중에는 버튼 비활성화 또는 스피너 등으로 진행 상태를 표시한다.
- 네트워크·권한 등의 요청 실패를 화면에 표시한다.
- 브라우저 저장소만 사용하는 CRUD로는 충족하지 못한다.

### 배포와 제출 — PDF 2쪽, 4~6쪽

- 외부에서 접속할 수 있는 URL과 GitHub 저장소 URL을 제출한다.
- 배포 환경에서 목록·상세 조회와 등록·수정·삭제가 모두 동작해야 한다.
- README에 로컬 설치·실행 명령어와 기술 스택을 명시한다.
- PDF는 API Key 등 민감 정보를 .env에 저장하고 .gitignore에 .env를 포함하며, 키가 포함된 코드를 GitHub에 푸시하지 않도록 요구한다.
- 배포 환경의 환경변수도 별도로 설정한다.
- Vercel·Netlify는 배포 예시이며 특정 플랫폼을 필수로 지정하지는 않는다.

## 4. 선택 사항과 비필수 범위 — PDF 5~6쪽

- 보너스: Context 등의 전역 상태, useMemo/useCallback/React.memo 중 하나 이상의 메모이제이션, Supabase/Firebase Auth와 보호 라우트.
- TypeScript는 선택이며 사용 자체에 가산점은 없다. JavaScript만으로 수행할 수 있다.
- 반응형 디자인은 선택이다.
- 스타일링 방식은 자유다. 순수 CSS, CSS Modules, Tailwind CSS, CSS-in-JS, UI 라이브러리 등이 허용된다.
- 백엔드 서버 직접 구현과 고급 권한/RLS/Rules·복잡한 관계 설계는 필수가 아니다.
- 시각적 완성도보다 React 구조와 데이터 흐름이 우선이다.

## 5. 학습 목표 — PDF 2쪽

자신의 구현을 바탕으로 다음을 설명할 수 있어야 한다.

- 컴포넌트가 필요한 이유와 분리 기준.
- props와 state의 차이, 상태 배치와 데이터 흐름.
- useEffect의 실행 시점·의존성과 데이터 요청의 관계.
- 비동기 로딩·성공·실패·빈 상태의 UI 표현.
- 한 기능에서 라우팅 → 컴포넌트 → 상태 → 이벤트 → 렌더링이 연결되는 과정.

## 6. 기존 프로젝트 활용 가능성과 변경 규모

포트폴리오 주제를 재사용하여 프로젝트 기록 CRUD 서비스로 발전시키는 것은 가능하다. 다만 기존 HTML을 React 페이지·컴포넌트로 재구성하고, DOM 조작 코드를 React 상태 중심으로 재작성하며, 라우팅과 원격 CRUD를 추가해야 한다. 검증·배포·문서도 새 구조에 맞춰 구성해야 하므로 작은 기능 추가 수준은 아니다.

B1-1의 폼 검증, 로딩·실패 처리, 중복 제출 방지, 필터링 경험은 활용할 수 있다. 기존 JavaScript를 그대로 옮기는 것만으로 요구사항을 충족하지는 못한다.

## 7. 이번에 결정한 범위와 남은 결정

사용자는 B1-1을 유지하고 별도 codyssey_B1-2 디렉터리에서 새 과제를 시작하기로 했다. B1-2 요구사항 PDF는 B1-1에서 이 프로젝트의 docs로 이동한다.

현재 단계에서는 서비스 주제, 데이터 모델, Supabase/Firebase 선택, 개발·배포 도구, 세부 진행 순서를 결정하지 않았다. Git 저장소 초기화, 의존성 설치, React 프로젝트 생성, 구현도 이번 작업에 포함하지 않는다.

B1-1의 React 금지·기존 소스 구조 등의 과제별 지침은 B1-2에 그대로 적용할 수 없다. B1-2 작업 지침과 진행 체크리스트는 후속 단계에서 새 과제 요구사항에 맞게 정리할 필요가 있다.
